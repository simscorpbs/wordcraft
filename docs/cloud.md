# AutoSave in synced cloud folders

> **Last reviewed:** 2026-10-21 · **Last updated:** 2026-10-21 · **Change:** AutoSave is on for every saved file, local or in the cloud, and remembered per file; version history keeps original bytes, follows renames and moves, and uses OneDrive's automatic retention · **Target:** Microsoft Word (Microsoft 365) for Mac 16.113.4

WordCraft uses the desktop sync clients' ordinary folders. It does not connect to a cloud API. A file saved in one of these folders is uploaded by the installed client and becomes available on the person's other devices.

## Folder discovery

On macOS, WordCraft checks `~/Library/Mobile Documents/com~apple~CloudDocs` for iCloud Drive, each `GoogleDrive-<account>` and `OneDrive-<account>` under `~/Library/CloudStorage`, then older `~/Google Drive` and `~/OneDrive` folders. On Windows, iCloud Drive is `%USERPROFILE%\iCloudDrive`. Google Drive may be a drive letter whose root contains `My Drive` (including localized client names), or a mirrored profile folder. OneDrive uses `%OneDriveConsumer%`, `%OneDriveCommercial%` or `%OneDrive%`. On Linux and other systems there is no assumed client path; `WORDCRAFT_CLOUD_ICLOUD`, `WORDCRAFT_CLOUD_GDRIVE` and `WORDCRAFT_CLOUD_ONEDRIVE` can name folders. The browser build has no folders to discover.

The desktop host discovers roots once. `file.cloud={}` reports provider, root, current path, conflict state and discovered roots. Provider ids are `icloud`, `gdrive` and `onedrive`. iCloud-only files must be downloaded by the sync client before opening.

## Save a new document

The Save to Cloud dialog asks where AutoSave should keep a new document. `file.saveToCloud` accepts optional `provider` (`icloud`, `gdrive` or `onedrive`) and `name` (without extension). With no provider, the first discovered root is chosen in iCloud Drive, Google Drive, OneDrive order. The file is written as a new `.docx` in that provider's documents folder, using a numbered name when needed.

This is the same basic model Word uses when a new document is saved to OneDrive: Word chooses a synced location and its client handles upload. WordCraft does not provide Microsoft's service integration or coauthoring features.

## Closing and switching documents

With AutoSave enabled, an edited document closes, opens another document or creates a new document after WordCraft writes the pending changes with `file.save` and {"ifUnchanged":true}. The action continues without a Save Changes prompt. If another device changed the file, the Save Conflict dialog stays open and the document remains open. If Save Changes was already visible, a successful AutoSave closes that prompt and continues the pending action. With AutoSave disabled, the existing Save Changes behaviour remains.

## AutoSave for each file

AutoSave is on by default for every document whose file exists on disk in a format that keeps everything (`.docx`, `.docm`, `.dotx`, `.dotm`, `.odt`, `.rtf`, and WordCraft's own `.json` and `.xml`). This covers local files as well as files in iCloud Drive, Google Drive or OneDrive folders, and an opened file is covered at once, without a save first. Word turns AutoSave on by default only for files stored in OneDrive or SharePoint. WordCraft also covers local files because the project owner decided so. The disk stamp read when the file is opened protects a local file in the same way as a cloud file.

The switch is still off, with the reason in its tooltip, for a new document that has never been saved, a previous version opened from the history, a format that does not keep everything, the browser, and a file with a conflict waiting. A file opened from bytes, or a recovered document, needs an explicit save before AutoSave writes it, because WordCraft has no disk stamp to check first.

A write that fails, for example because another program holds the file, does not turn AutoSave off. AutoSave pauses and tries again after 5 seconds, then waits twice as long after each further failure, up to one minute. The status bar shows the error while writes keep failing, and the message goes away after the next successful write. The remembered choice for the file does not change.

Each file remembers its switch, as Word remembers it for each document. Turning AutoSave off for a file is remembered when the file is opened again, including in later runs. Turning it back on forgets that choice. The choices are kept in `<settings_dir>/autosave.json`, never in the document, so remembering one does not change the file's bytes. Paths are normalized: on Windows the `\\?\` prefix of canonical paths is removed, separators become `\` and letter case is ignored, and letter case is also ignored on macOS. The file keeps at most 2000 entries, drops the oldest first, is read only up to 1 MiB and is written atomically through a temporary file. Renaming a file (`file.rename`) keeps its choice. Save As, Save to Cloud and Keep both give the new file the switch the document had. The browser build keeps no choices.

File › Options › Save › **Turn on AutoSave by default** sets the default for files with no choice of their own (`file.options` with `{"autosaveByDefault": bool}`, saved with the app's settings as `editing.autosaveByDefault`). It is on by default. When it is off, a file is AutoSaved only after the user turns the switch on for it, and that choice is remembered for the file too.

`file.autosave` with `{"value": bool}` (or `{}` to toggle) sets the open document's switch and remembers it for the file, exactly as the title bar switch does. In the app it fails, with the reason, when AutoSave cannot cover the document. To read the state without changing it, use `file.cloud={}`. Its `autosave` object has `on` (the switch), `default` and `remembered` (`true`, `false`, or `null` when the file follows the default). In the app it also has `covers` (whether AutoSave writes the file), `blocked` (the reason it cannot, or `null`) and `failing` (the last write error while writes keep failing, or `null`).

File › Home and Open list each file once in Recent, using the same path rules without reading the disk. On Windows, `C:\Docs\A.docx` and `c:/docs/a.docx` are one entry.

## Version history

The desktop app keeps a local history for each saved document under `<settings_dir>/versions/<path hash>/`, where the hash is taken from the canonical path. On Windows the path is lower-cased first, because file names there ignore case. A folder made by an earlier build under the case-sensitive hash is moved to the new name the first time it is looked up. Each version is described in `index.json` by `id`, `savedAt` (UTC), `author`, `size` (the saved document's size), `kind` (`save`, `autosave`, `restore` or `original`), `windowStart`, `digest` (SHA-256 of the saved bytes), `session`, `capturedAt`, `storage` (`whole` or `parts`) and `stored` (the disk space the version added). Every file the history writes is flushed and read back before it replaces anything. `document.json` records the path the folder last belonged to. History is written in the background. A failure in the history is reported and logged. It never stops a save and never changes the bytes saved. Only the document's own file has a history: a copy exported in another format, such as PDF or plain text, does not create one.

Every explicit save creates a version. Word's AutoSave on OneDrive adds a version at the first change after a document opens and then about every ten minutes. WordCraft does the same: the first AutoSave write of each editing session (one opening of the document) starts a new version, and later writes from that session update it until ten minutes have passed since the version was started. The last write before the document closes is therefore always in the history.

Before any save writes over a file whose current bytes are not already in its history, WordCraft stores those bytes as an `original` version. `savedAt` is the file's modification time. This covers a `.docx` made before WordCraft was installed, a file another program changed while it was open or closed, and the file that Save As replaces. The copy is written synchronously, before the file is replaced. The file is read once for each opened document, and later saves only compare the disk stamp.

A `.docx` is a zip archive whose parts are compressed separately, so a one-letter edit changes most of the file's bytes and a byte diff of two saves is almost as large as the file. The history therefore opens the archive and keeps each part as an object in `objects/`, named by the SHA-256 of its content, as git names its blobs. A picture, font or style part that did not change between saves is stored once. A part that changed is stored as a delta against the same part of the previous version: the shared start and end are copied, and the rest is matched in 32-byte blocks with a rolling hash. The delta is then compressed. After ten deltas in a row, or when a delta would be more than half the size of the compressed part, the part is stored whole again. A restore therefore reads at most eleven objects for a part, and one damaged object affects only the versions whose chain passes through it.

Each version kept this way is a manifest, `<id>.parts.json`, that lists the parts in archive order with their names, compression method, dates, sizes and hashes, and repeats the version's metadata. Opening, restoring or saving a copy rebuilds the archive from the manifest. Every part is checked against its hash. The rebuilt zip can differ from the saved file in its compressed bytes, but each part has the same content. Before a version is stored as parts, the archive is rebuilt in memory and split again to confirm that it comes back with the same parts. The `original` version, the bytes that were on disk before WordCraft wrote over them, is always kept byte for byte as `<id>.bin`. So is any file that is not a zip or that exceeds the limits: more than 10,000 parts, one part over 256 MiB, or more than 1 GiB in total uncompressed. Those limits are checked against the sizes the archive declares, and every read is capped at the declared size, so a zip bomb is stored whole and never inflated. If anything in the parts path fails, the version is stored whole instead.

An object that already exists is reused only if it still reads back correctly. A damaged object is written again whole, which also repairs every version that uses it. Versions that earlier builds stored whole remain readable as they are and move to parts gradually, one per save, newest first, after their parts are confirmed to read back. As a measure, 100 versions of a 1.8 MB `.docx` with a 1.7 MB picture and one paragraph edited each time take 180 MB stored whole and 2.9 MB stored as parts, 1.6%.

Retention follows the automatic version limits of SharePoint and OneDrive for work. All versions are kept for 30 days. From 30 to 60 days, the newest version of each hour is kept. From 60 to 180 days, the newest of each day is kept. After that, the newest of each week is kept. Age alone never empties a history. Each document keeps at most 500 versions and 500 MiB of real disk space, newest first, with a part shared by several versions counted once. Objects that no kept version needs, either directly or as the base of a delta, are deleted after pruning. If any manifest or object header cannot be read, nothing is deleted on that pass. The oldest `original` version is pinned: it outlives the time rules and is the last version to go under the count and size limits. A personal OneDrive keeps only the last 25 versions; the local history keeps more because it is private to the computer. A damaged `index.json` is read one entry at a time. Version files that the index does not mention are listed again from their own files, so pruning never deletes them only because the index lost them. A version whose bytes no longer match its digest is refused.

The history follows the document. `file.rename` moves its folder to the new name, as OneDrive keeps a file's history through a rename or move. Save As, Save to Cloud and Keep both write a new file whose history starts with that save, and the original file keeps its own history. This is the same as copying a file in OneDrive, where only the latest version comes along. When a file with no history is opened or saved, WordCraft looks for the folder of a file that was moved or renamed outside the app. A folder matches when its recorded path no longer exists and its newest version has exactly the bytes now in the file. A copy, whose original still exists, never takes the history. A file that was both moved and edited outside WordCraft starts a new history with its current bytes as the `original`.

`file.versions={}` lists versions newest first and returns `{id,savedAt,author,size,stored,kind}`, where `stored` is the disk space the version added. The index is read when the call is made, so the first call after a document opens already returns its versions. `file.versions={"open":"id"}` opens an older version as a separate, read-only document named `Name (version <local date time>)` (see below). `file.versions={"restore":"id"}` replaces the current content in one Undo step. Unsaved changes are first stored as an `autosave` version, so the state before the restore stays in the history. The restored bytes are then recorded at once as a new `restore` version, whether or not AutoSave writes the file afterwards. The listing can also show the `original` kind. The legacy `{"save":"label"}` and numeric `{"restore":index}` forms remain available for compatibility.

File > Info > Version History opens the right-hand history pane. Clicking the document name in the title bar (left or right button) opens a small file menu, as Word does for a OneDrive document: the file name, which can be changed there and applied with Enter (`file.rename`); the folder that holds the file, or Not saved; and Version History. The pane lists versions newest first under day headings: Today, Yesterday, or the date (month names in English and Portuguese, an ISO date in other interface languages). Each row shows the local time and the author, with an Open version link; hovering a row shows its full date and time, and right-clicking it offers Open version and Restore. With no versions the pane says why: the document has not been saved yet, the history is empty, or (in the browser) the history is kept by the desktop app.

Before a version is opened or restored, AutoSave writes the current document if it has unsaved changes, so that state is in the history too. An opened version is read only. Commands that would change it, including Undo and Redo, are refused with a status-line message; file commands, the view, moving the insertion point, selecting and copying still work. Its row in the pane is highlighted and has no link, and the title bar reads `Name (version <local date time>) — Previous version`. A Previous version bar above the page shows the date, time and author with **Compare**, **Restore**, **Save a copy** and **Close**.

- **Compare** (`file.compareVersion={}`, same options as `review.compare`) shows the previous version as the original and the current document as the revised one, with the differences as tracked changes. The comparison takes the version's place and stays read only; pressing Compare again shows the version.
- **Restore** first returns to the current document, then runs `file.versions={"restore":"id"}`: the version becomes the document's content in one Undo step and is recorded at once as a `restore` version.
- **Save a copy** saves the version as a new file and then returns to the current document.
- **Close** (`file.closeVersion={}`) returns to the current document as it was: its unsaved changes, password and AutoSave disk stamp are kept while the version is shown and put back.

WordCraft has one document per window, so the version is shown in the document's own window instead of a separate one. New, Open and Close while a version is shown first return to the current document. Close stops there, as closing the version's window would in Word, and New and Open then save or ask about the document's changes as usual. Quitting the app does the same, so a shown version never hides unsaved work.

WordCraft keeps a disk stamp with size, modification time and a fast byte digest. AutoSave calls `file.save` with `ifUnchanged`. If another device or program changed the bytes, or the file is missing because it was moved or deleted, AutoSave does not overwrite it. It records `changed` or `missing` and pauses. A timestamp-only touch with identical bytes is accepted.

The Save Conflict dialog offers **Keep both**, **Keep this version**, **Open the other version**, **Decide later**, and **Save it here again**. `file.resolveConflict` takes `{"keep":"both"}`, `{"keep":"mine"}` or `{"keep":"theirs"}`. `both` writes `Name (conflict copy).docx` beside the other version and edits the copy. `mine` overwrites the path. `theirs` reopens the file on disk and cannot reopen a missing file. When the file is missing, the dialog offers only **Save it here again** (`mine`, which writes the document back to its original path) and **Decide later**.

## Limits

The feature depends on a compatible sync client being installed and signed in. There is no cloud API, server-side merge or real-time coauthoring. The version history described above is local to the desktop profile, is not synchronized between devices and is unavailable in the browser. iCloud Drive, Google Drive and OneDrive keep their own server-side histories; WordCraft does not browse or merge those histories.
